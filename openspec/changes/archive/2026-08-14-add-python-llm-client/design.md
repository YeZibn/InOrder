## Context

仓库当前没有应用代码或既有接口约束。该 change 需要引入 Python 基础结构和一个可供后续 LangGraph 节点调用的模型访问边界，同时保持供应商协议细节隔离。详见 proposal.md 的动机与范围，行为契约见 specs/llm-client/spec.md。

## Goals / Non-Goals

**Goals:**

- 建立单一、可注入的同步文本调用边界。
- 默认兼容 OpenAI-style chat completions，允许通过 base URL 使用兼容网关。
- 统一配置、响应和错误模型，支持有限重试和安全日志。
- 为推理模型提供可选 reasoning effort 配置，默认不发送该参数以保持中转站兼容性。
- 用 mock 覆盖主要成功与失败路径，并提供手工验证入口。

**Non-Goals:**

- 不在本阶段构建 LangGraph 图或拉货业务状态。
- 不实现流式响应、工具调用、结构化输出、RAG、embedding 或多模态。
- 不封装供应商之间的高级差异，也不持久化会话记录。

## Decisions

### 使用 OpenAI-compatible Python SDK 作为传输层

通过 SDK 的 chat completion 接口和可配置 base URL，优先覆盖主流云端服务与内部兼容网关。相比直接使用 HTTP，可减少请求序列化和认证细节；相比绑定单一供应商，可保留迁移空间。供应商专属 SDK 暂不引入。

### 采用配置对象与环境变量适配器分离

环境变量只负责构造配置对象，客户端接受显式配置对象，便于测试和未来从 Web 配置中心注入。API key 仅保存在内存配置中，不写入日志或响应。`LLM_REASONING_EFFORT` 只允许 `low`、`medium`、`high`，未设置时保持 `None`。

### 使用 Chat Completions 的可选 reasoning_effort 参数

当前客户端使用 Chat Completions，因此在配置存在时将 reasoning effort 作为 `reasoning_effort` 请求参数传递；未设置时完全省略该字段，避免不支持该参数的兼容网关报错。实际可用值仍取决于所选模型和中转站能力。

### 定义应用层响应和错误类型

客户端返回包含文本、模型标识、可选 usage 和原始响应元数据的轻量结构；认证、限流、超时、参数和通用上游错误分别建模。这样 LangGraph 节点不需要依赖 SDK 异常类型。

### 只对可安全重试的请求执行有限重试

对超时和明确的临时上游错误执行有限次数、带退避的重试；认证和参数错误不重试，限流遵循上游提供的等待信息且受最大次数限制。当前调用是无副作用的文本生成，因此重试风险可控。

### 使用 pytest 与 HTTP/SDK mock

测试隔离真实网络，验证配置解析、请求映射、响应归一化、错误分类和重试次数。手工入口单独保留，供开发者用真实凭据做冒烟验证。

## Risks / Trade-offs

- [兼容接口差异] → 仅依赖通用 chat completion 字段；遇到不兼容供应商时通过适配层扩展，不污染调用方。
- [重试放大成本或延迟] → 默认小次数、指数退避并允许配置；记录重试次数但不记录敏感请求内容。
- [模型输出不稳定] → 本阶段只承诺返回文本，不对内容质量做业务判断；后续由具体工作流增加校验。
- [真实凭据验证缺失] → CI 使用 mock，手工入口提供清晰的配置检查和非敏感错误提示。

## Migration Plan

这是空仓库中的首个基础能力，不涉及既有数据迁移。实现后先通过 mock 测试，再使用开发环境凭据运行验证入口；若需要回滚，移除新增 Python 模块和依赖即可。

## Open Questions

无。模型供应商、默认模型和部署方式可以在实现时通过环境变量决定，不改变本阶段接口契约。
