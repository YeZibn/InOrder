## Context

当前 `MAIN_INTENT_SYSTEM_PROMPT` 的 `order` 定义锚定「要求系统执行、创建、修改或查询订单相关操作」，边界示例全是显式命令（创建订单/修改草稿/查询历史），导致用业务目标语言表达的订单需求（如「我想从上海运货到温州」）被判 `qa`。同理，`SUB_INTENT_SYSTEM_PROMPT` 的 `create_order` 描述为「创建新订单草稿」，子意图提取层也存在「运货/发货」→ `create_order` 的语义鸿沟。见 proposal.md - Why。

## Goals / Non-Goals

**Goals:**
- `order` 主意图覆盖业务目标愿望陈述，判据为期望输出（行动 vs 信息）而非命令动词。
- prompt 注入运输领域映射，让「运货/发货/配送」在主意图与子意图两层都能被识别。
- 咨询信号闸门词防止过度归 `order`。
- 钉死字面派判定边界（能力咨询归 `qa`）。

**Non-Goals:**
- 不实现对话策略层（如 `qa` 回答后主动引导下单）。
- 不新增主意图类别，不改图路由结构，不改 `IntentModel` Protocol 接口。
- 不引入真实 LLM 评测集（评测仍以单测断言为主，评测集待后续）。

## Decisions

**D1: order 锚点转向「期望输出」。** 判据从「是否含命令动词」改为「用户期望输出是行动/结果还是信息」。理由：业务目标陈述（运货）与系统操作（下单）语义同义，要求用户用系统语言反直觉。备选：维持窄锚点 + 让用户改述——体验差，否决。

**D2: 领域映射注入主 + 子两层 prompt。** `MAIN_INTENT_SYSTEM_PROMPT` 增加「运货/发货/配送/托运/下单 = `order` 业务目标」说明；`SUB_INTENT_SYSTEM_PROMPT` 增加「运货/发货/配送需求映射为 `create_order`」说明。理由：仅改主意图则子意图提取仍会失败，两层都需跨过语义鸿沟。备选：仅改主意图——子意图会漏，否决。

**D3: 咨询信号闸门词。** prompt 列出 了解/咨询/怎么/多少钱/能不能/一般 等信号，存在时即使提及业务目标也归 `qa`。理由：扩宽 `order` 后需防过度归 `order`。

**D4: 字面派原则。** 意图分类只认字面期望输出；「能运吗」问能力归 `qa`，深层需求推测交对话策略层。理由：保证分类可解释、可预期；分类器不该替用户说没说的话。

## Risks / Trade-offs

- [过度归 order] → 闸门词 + 能力咨询 scenario 钉死边界；测试覆盖反向 case。
- [边界 case 漂移] 「能运吗」类纯字面派判定可能漏掉真实下单意图 → 接受；由对话策略层补偿，不靠分类器猜测。
- [无真实 LLM 评测] → 评测以 prompt 内容断言 + mock 路由测试为主；分类准确率待评测集。
