## Context

当前项目已有可注入的 Python LLM 客户端，但没有主图、订单图或问答图。该 change 只建设一个可独立测试的意图规划子图，输出供未来图编排使用的结构化计划。行为契约见 specs/intent-planning/spec.md。

## Goals / Non-Goals

**Goals:**

- 用 LangGraph 风格的节点边界组织意图识别流程。
- 支持主意图单分类、订单子意图多标签提取和依赖关系建模。
- 输出稳定的 IntentPlan 数据结构，并在低置信度或信息不足时要求澄清。
- 允许通过现有 LLMClient 注入模型调用，以便 mock 测试。

**Non-Goals:**

- 不实现订单创建、修改、历史查询、报价、确认或问答回答。
- 不连接数据库、外部订单 API 或业务工具。
- 第一阶段不支持并行分支、条件分支、复杂多轮记忆或自动执行计划。

## Decisions

### 将输出定义为 IntentPlan 而非多标签数组

仅返回 `['query_history_order', 'modify_draft']` 会丢失动作顺序和数据依赖。IntentPlan 中每个步骤拥有稳定 ID、参数和 `depends_on`，下游图可以在不重新理解原文的情况下消费它。

### 采用顺序依赖作为第一阶段关系模型

“查询历史订单后修改草稿”是首个明确场景，因此只实现顺序和结果引用。并行、条件和循环关系留给后续 change，避免第一版引入通用工作流规划器的复杂度。

### 分离主意图、子意图与执行状态

主意图回答“属于订单还是问答”，子意图回答“需要哪些原子动作”，`needs_clarification` 回答“计划是否足够明确”。本子图不保存订单业务状态，也不把确认动作当作独立订单子意图。

### 使用结构化模型输出并做确定性校验

LLM 负责候选提取和关系判断；应用层校验枚举值、步骤 ID 唯一性、依赖存在性、无环顺序和澄清字段完整性。校验失败时返回澄清或识别错误，不执行任何业务副作用。

### 子图节点边界

```text
classify_main_intent
  → extract_sub_intents
  → normalize_sub_intents
  → build_intent_plan
  → validate_intent_plan
```

每个节点只读写图状态中的识别字段，最终节点返回 IntentPlan；未来主图将根据 `main_intent` 和计划内容路由到下游子图。

## Risks / Trade-offs

- [自然语言中的隐式依赖难识别] → 保留原始参数和澄清状态，宁可要求澄清也不虚构依赖。
- [LLM 输出格式不稳定] → 使用结构化输出约束，并在应用层做枚举、引用和环路校验。
- [子意图集合过早固化] → 第一阶段只承诺三个订单子意图，后续通过新增枚举和规格扩展。
- [主意图混合请求] → 输出 `ambiguous`，暂不自动跨订单与问答图执行。

## Migration Plan

这是新增能力，不涉及既有数据迁移。先以纯内存状态和 mock LLM 完成单元测试，再由未来主图接入；回滚时移除意图子图模块，不影响现有 LLM 客户端。

## Open Questions

无。并行/条件依赖和更多子意图可在后续需求中单独设计。
