## Context

当前 `cargo_profile` 解析器围绕原始表达、字段来源和不确定性维护了较多嵌套字段。新的画像需要直接服务于未来的载重、空间和长宽高边界校验，并且仍由 LLM 负责物流常识估算。

## Goals / Non-Goals

**Goals:**

- 将画像和汇总收敛为稳定、直接可消费的 JSON 结构。
- 让模型优先估算核心规模字段，而不是因未明确提供就返回空值。
- 用单一 `reason` 保留必要解释，区分明确值、推导值、估算值和不可估算状态。
- 让完全缺失信息时的 `null` 成为显式、可解释的结果。

**Non-Goals:**

- 本 change 不实现车辆目录、车型推荐、车型筛选或装箱算法。
- 不在本地代码中根据货物名称补算重量、体积或尺寸。
- 不为旧画像增加兼容解析；旧画像由重新生成得到新结构。

## Decisions

### 1. 使用直接字段表达单位

画像使用 `weight_kg`、`volume_m3` 和 `dimensions_cm`，删除独立 `unit` 字段。这样下游车辆校验可以直接读取字段，不需要解释元数据。

备选方案是保留现有字段级元数据，但会重复表达单位并增加 schema 复杂度，因此不采用。

### 2. 用一个必填 reason 替代来源元数据

LLM prompt 要求每条画像输出非空 `reason`，说明数值来源、估算假设和无法估算的原因。删除 `raw`、`basis`、`confidence`、`warnings`，避免画像契约过度膨胀。

备选方案是保留 `basis`/`confidence`，可机器化区分可信度，但与当前“先简化结构”的目标冲突；后续若车辆校验需要风险分级，可再单独增加校验结果字段。

### 3. 核心字段采用“尽力估算，完全不足才为空”

只要输入包含重量、数量、包装、体积或尺寸中的可用信息，模型就必须尽力生成总重量、总体积和整体尺寸的具体值；仅有货物名称等无法确定本次运输规模时，才允许返回 `null`。

### 4. 汇总只保留直接数值

`cargo_profile_summary` 保留 `total_weight_kg`、`total_volume_m3` 和必要的汇总 `reason`，不再携带状态字段。任一货物无法估算对应指标时，该汇总指标返回 `null`。

## Risks / Trade-offs

- [LLM 估算可能不准确] → 强制 `reason` 描述假设；车辆校验阶段将估算结果视为初步约束，而非用户确认事实。
- [删除 basis 后机器无法区分明确值和估算值] → 当前阶段优先结构简洁；需要风险分级时在车辆校验模块增加独立的校验状态。
- [旧 OrderContext 中的画像结构不兼容] → 画像更新时基于完整原始货物重新生成并整体替换，不读取旧画像。
