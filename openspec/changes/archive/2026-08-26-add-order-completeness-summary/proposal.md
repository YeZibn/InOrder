## Why

当前工作流虽然能够提取、合并订单字段并估算车型，但最终输出主要是 Rewrite、Extract 和内部处理状态，用户无法快速知道订单已经识别了什么、还缺少什么。需要在订单子图末尾增加确定性的完整性检查和业务摘要，让系统在缺少必要信息时明确提醒用户补充。

## What Changes

- 在订单子图的车型处理之后增加最后一个订单完整性检查与总结节点。
- 使用规则检查最小可处理订单所需字段：装货地、卸货地、货物名称、重量或数量、送达时间。
- 区分必填缺失和可选缺失；车型允许由系统估算，不作为默认硬性缺失项。
- 同时输出面向程序的结构化状态，以及面向用户的自然、礼貌、可直接继续对话的订单回复。
- 用户回复采用“已识别内容 + 仍需补充信息 + 具体示例”的表达方式，不直接展示 `incomplete`、`missing_required`、内部字段名或节点名称。
- 将业务摘要作为 CLI、SSE `DONE` 事件和前端最终结果的主要展示内容，保留结构化详情供调试。
- Web 前端收到订单流的 `DONE` 事件后，除更新右侧摘要面板外，还必须将面向用户的 `user_message` 作为一条助手消息追加到主对话框，确保用户在会话流中直接看到最终订单结论或补充提示。
- 不使用 LLM 判断字段是否必填或修改已确认的订单事实；本次先使用规则模板生成自然回复，LLM 语言润色作为后续可选增强，不纳入本次范围。

## Capabilities

### New Capabilities

- `order-completeness-summary`: 基于最终订单上下文检查必填字段并生成用户可读业务摘要。

### Modified Capabilities

- `order-processing-subgraph`: 在车型处理后执行订单完整性检查与总结节点，并返回其结构化结果。
- `workflow-sse-events`: 在 `DONE` 终态事件中提供订单摘要和完整性状态，供客户端展示。

## Impact

影响订单 LangGraph 子图状态、CLI 结果格式、SSE `DONE` payload 和前端最终结果展示；不改变 Rewrite、Extract、货物画像或车型估算的既有输入输出契约，也不引入新的外部服务或数据库依赖。
