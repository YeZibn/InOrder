## Context

订单子图当前已经在上下文合并后执行货物画像和确定性车型解析，并将结构化结果返回给父图。现有 CLI 和 Web 展示仍偏向内部处理过程；本 change 在订单子图末尾增加一个只读的完整性与摘要层，复用最终 `OrderContext`，不改变前序解析节点。

## Goals / Non-Goals

**Goals:**

- 在车型处理之后统一判断订单是否满足最小处理条件。
- 生成可供 CLI、SSE 和 Web 使用的稳定结构化摘要。
- 对缺少的必填字段给出字段标识、用户标签和下一步提示。
- 保留完整 `OrderContext` 与现有结果字段，保证下游兼容。

**Non-Goals:**

- 本次不实现真实下单、联系人/手机号等正式履约校验的固定策略。
- 不使用 LLM 判断必填字段、修改事实或专门生成摘要。
- 不引入数据库、外部订单服务或新的模型依赖。

## Decisions

### 1. 将完整性检查作为订单子图最后一个节点

节点读取车型处理后的最终上下文，输出 `order_summary`。这样摘要能够同时看到路线、货物画像、车型和送达时间，又不会反向影响 Rewrite、Extract 或车型估算。若前序节点失败，沿用现有错误路径，不生成部分摘要。

### 2. 使用规则校验最小字段

规则默认要求：可用的 pickup、可用的 dropoff、至少一个货物名称、重量或数量至少一个、有效 `delivery_time`。位置对象至少包含 `city` 或 `full_address`；时间必须是订单时间而非历史查询时间，并具备可用的绝对时间边界。车型缺失不判定为缺失，因为车型节点可以估算。

### 3. 区分结构化摘要和用户回复

`order_summary` 建议包含结构化字段和一个单独的 `user_message`：

```json
{
  "status": "complete|incomplete",
  "summary": "已识别从温州发往上海的苹果运输需求。",
  "facts": {"route": {}, "cargo": [], "delivery_time": {}, "vehicle": {}},
  "missing_required": [],
  "missing_optional": [],
  "next_prompt": "",
  "user_message": "已为您整理好这笔运输需求……"
}
```

摘要事实只从 `OrderContext`、货物画像和车型解析结果组装；缺失字段使用稳定的 `field` 与 `label`。重量和数量作为一个组合必填项，避免重复提示。

### 4. 使用面向用户的自然文案

本次直接用确定性模板生成自然语言回复。完整订单使用“已为您整理好……可以继续下单”；信息不足时使用“目前已为您识别……为了继续为您安排，还需要补充……”并根据字段附带输入示例。结构化字段仍保留给程序使用，但 CLI、SSE 客户端和 Web 优先展示 `user_message`。未来若增加 LLM 润色，调用必须接收规则生成的事实和缺失字段，只允许改写语言，失败时回退到规则版本。

### 5. 在公开终态中增加回复而不删除旧字段

订单子图将结构化摘要和 `user_message` 放在结果的新增字段中；SSE `DONE` 事件同时保留现有 `order_result`，并携带自然语言回复。CLI/Web 优先展示用户回复，调试面板继续展示完整结构化结果。

### 6. 在 Web 主对话框展示最终摘要

Web 客户端收到订单流的 `DONE` 事件后，从 `result.order_result.order_summary.user_message` 读取最终用户文案，并兼容读取顶层 `result.order_summary.user_message`。客户端 SHALL 将该文案追加为主对话框 `#messages` 中的一条 `assistant` 气泡，同时更新右侧摘要面板和结构化结果面板。处理中阶段事件只更新已有进度气泡；不得把内部节点状态、原始 JSON 或 `complete`/`incomplete` 等程序字段追加到主对话框。非订单结果或缺少摘要的兼容响应不新增订单摘要气泡，避免产生误导；同一个 `DONE` 事件只能追加一次助手摘要消息。

## Risks / Trade-offs

- [业务必填规则未来变化] → 将规则集中在完整性检查模块，并让联系人、手机号等正式履约字段通过可配置规则扩展。
- [历史订单时间被误当作送达时间] → 只接受 `new_order` 语义且经过时间归一化的 `delivery_time`。
- [摘要与结构化字段不一致] → 摘要生成只读同一份最终上下文，并增加字段级测试。
- [前端暂不识别新增字段] → 保留旧结果字段；新客户端可渐进使用 `order_summary`。

## Migration Plan

先实现节点和结果契约，再更新父图/SSE、CLI 和 Web 展示，最后补充完整性场景测试。回滚时可移除最后节点及新增结果字段，前序订单解析链路不受影响。
