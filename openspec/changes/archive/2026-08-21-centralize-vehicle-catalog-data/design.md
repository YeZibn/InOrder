## Context

现有 `catalog` 已提供车型关键词查询，但车型记录与能力字段尚未形成独立的主数据层；部分词汇常量和后续车型能力表存在重复维护风险。实现需要兼容现有 extract、normalization 和测试使用的 canonical code。

## Goals / Non-Goals

**Goals:**

- 建立一个独立、可审阅的车型主数据文件作为唯一事实来源。
- 统一基础车型、标准车长和特殊规格的记录结构，并补齐能力范围。
- 让现有 catalog 查询 API 从主数据加载，保持现有匹配结果。
- 删除旧的重复数据定义，并用结构测试防止遗漏或重复。

**Non-Goals:**

- 不在本变更中实现 LLM 选车、装箱优化、多车拆单或成本计算。
- 不改变 extract 保留原文的契约，也不改变车型模糊匹配的阈值和决策策略。

## Decisions

1. **以独立 JSON 主表存储记录。** JSON 便于审阅、版本管理和未来由运营侧维护；Python 代码只负责加载、校验和查询，不再内嵌第二份完整表。
2. **基础车型与特殊规格分层。** 基础车型记录能力范围；特殊规格单独记录并通过 code 组合，冷链不创建新的基础车型 code。
3. **使用范围字段而不是单一推测值。** 长宽高、体积和载重采用 `*_min`/`*_max` 字段，保留当前已经确认的估算范围，避免伪造精确度。
4. **保留兼容 facade。** `catalog` 对外继续导出现有 `VehicleType`、`VehicleSpec` 和查找函数，内部统一从新表加载；迁移后删除旧数据定义文件/常量。

## Risks / Trade-offs

- [估算范围可能随业务经验调整] → 将表作为独立版本化数据，增加结构校验和逐车型测试，后续只改表即可。
- [JSON 字段错误导致运行时加载失败] → 加载时校验必填字段、code 唯一性、范围上下界和特殊规格集合，并在测试中覆盖。
- [旧调用方依赖旧字段] → 保留兼容查询接口和 canonical code；只有重复数据源被移除。

## Migration Plan

1. 创建新主数据文件并迁移当前确认的车型与规格记录。
2. 修改 catalog loader/facade、prompt 渲染和测试以读取新表。
3. 删除旧的重复车型表/常量，运行完整测试。
4. 若发现兼容问题，先恢复 facade 的字段映射；主数据文件可独立回滚。
