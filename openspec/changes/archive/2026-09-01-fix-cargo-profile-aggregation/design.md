## Context

当前上下文同时保存用户原始 `cargo` 和由其派生的 `cargo_profiles`/汇总。Reducer 会把同一货物的多轮 `add` 表达保存到数组中，画像节点随后以完整原始货物列表调用模型并整体替换派生画像。问题在于 Prompt 对数组累加语义描述不足，模型可能漏加重复记录。

## Goals / Non-Goals

**Goals:**

- 在画像请求契约中明确数组字段的累加语义和统一单位换算要求。
- 让模型输出的单货物重量、体积和整体尺寸反映该货物全部原始记录。
- 校验画像及汇总之间的算术一致性，发现明显漏加时触发格式修复或拒绝结果。
- 保持原始货物数据与派生画像分层，支持原始数据变化后的原子重建。

**Non-Goals:**

- 不把画像数值写回 `cargo`，不改变对外原始字段结构。
- 不在画像阶段引入车型选择或装箱算法。
- 不使用旧画像作为新一轮画像输入，也不实现画像的增量更新。

## Decisions

1. **Prompt 明确“数组即累加明细”**：在系统 Prompt 中给出 `weight=["1吨", "1吨"] → 2000kg` 等示例，并要求对每个数值数组先逐项解析、换算、求和，再进行密度/包装等估算。这样可直接修复 LLM 对多轮新增语义的歧义；相比在画像节点外部猜测自然语言单位，能覆盖数量、体积和尺寸等字段。

2. **保留双层数据模型**：`cargo` 是不可变更语义的用户原始记录；`cargo_profiles` 与汇总是可丢弃、可重建的派生缓存。画像节点继续在货物变化后从完整 `cargo` 重新生成并整体替换。相比把归一化结果写回原始记录，该方案可审计、可重试且避免重复累加。

3. **增加结果一致性校验**：解析成功后校验画像名称集合与原始货物集合一致，且汇总重量/体积与画像值之和一致（允许浮点误差）。若原始数据中的同类明确重量可解析，则画像对应重量不得低于这些明细的合计；不满足时走现有格式修复流程。校验只使用可确定的数值，不阻止纯常识估算。

4. **继续原子替换**：画像后端失败或结果校验失败时保留旧上下文，不写入部分画像；成功后一次性替换画像和汇总。该行为与现有更新器的深拷贝边界一致。

## Risks / Trade-offs

- [LLM 仍可能错误解析复杂单位或合并规则] → Prompt 提供正反例；增加确定性解析校验和格式修复重试；无法确定的字段仍按既有 `null` 规则处理。
- [严格合计校验可能拒绝合理的模型估算] → 仅校验明确可解析明细及画像间算术关系，不对常识估算值设定过窄误差范围。
- [多次重建增加 LLM 调用成本] → 仅在原始 `cargo` 发生变化时触发画像节点，未变化时复用现有派生结果。

## Migration Plan

1. 更新货物画像 Prompt 和解析后校验。
2. 增加重复新增、混合单位、多货物汇总及失败回滚测试。
3. 发布后观察画像日志中的校验失败率；必要时通过 Prompt 版本迭代调整估算示例。
4. 回滚时恢复旧 Prompt/校验逻辑，不需要迁移持久化数据；下一次货物变更会重新生成画像。
